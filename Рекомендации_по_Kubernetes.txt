    Все внешние зависимости (библиотеки) должны быть описаны в файлах описания зависимостей (например, в pom.xml, package.json).
        При этом мы не рекомендуем использование submodules. И рекомендуем всю кодовую базу одного приложения хранить в одном репозитории.
    В проекте должен быть и поддерживаться в актуальном состоянии README.MD файл, включающий в себя:
        Инструкции по сборке.
        Правила конфигурации приложения, то есть какие параметры и с какими значениями должны быть заданы для корректной сборки и запуска приложения
        Описание используемых внешних зависимостей (СУБД, очереди сообщений и так далее).
        Описание интеграций с внешними сервисами, если они есть.
        Если приложению требуются дополнительные системные пакеты, необходимо зафиксировать это в README.MD. По умолчанию мы стремимся уменьшить размер образа, поэтому не включаем такие пакеты как cURL, imagemagick, ping и gcc в список зависимостей.
        Команды выполнения миграций, прогрева кеша, добавления и изменения пользователей и т.д.
    Версии подключаемых библиотек должны быть зафиксированы, крайне не рекомендуется использовать latest версию.
    Приложения должны динамически конфигурироваться исключительно в рантайме и использовать для этого нативные средства Kubernetes (никакие настройки не указаны непосредственно в коде приложения, даже значения по умолчанию):
        Environment variables. Переменные окружения, которые попадут в контейнер.
        ConfigMaps
            Могут подключаться как файлы, монтируемые в файловую систему контейнера.
            Могут пробрасываться в контейнер как переменные окружения
        Secrets
            С точки зрения использования не отличаются от ConfigMaps, но предназначены для sensitive информации.
            Так же секреты могут автоматически подгружать данные из внешнего хранилища секретов, например, для HashiCorp Vault.
    Динамическое изменение кода в момент работы приложения не допустимо (включая правки кода через интерфейс администратора), все правки должны выполняться через git и доставляться в виде helm релизов.
    Приложения не должны хранить данные локально, они будут утеряны при перезапуске. Все персистентные данные должны сохраняться в БД, брокере сообщений, S3-хранилище.
    Приложение должно уметь работать в нескольких репликах. Рекомендуем запускать приложения в нескольких репликах на dev-стенде уже на ранних стадиях разработки, чтобы при разработке сразу отлавливать возможные ошибки. Все приложения в production среде должны быть запущены в нескольких экземплярах.
    Приложения должны корректно обрабатывать сигналы завершения от системы оркестрации. Приложение должно возвращать код выхода при завершении.
    Команды запуска приложения должны быть идемпотентны, т.е. корректно обрабатывать повторный или множественный запуск. Например, используя для этого транзакции. Это актуально, в том числе, для команд миграций или прогрева кэша.
    Разница между разными средами должна быть минимальной. Системное окружение и используемые инфраструктурные сервисы должны быть идентичны во всех окружениях.
    Логи приложения (а так же другая информация в значимых объёмах) не должны сохраняться в виде файлов внутри контейнеров – нужно писать либо в stdout, либо во внешний сборщик логов. Рекомендуемый формат логов - JSON. Примечание: тут буквально речь идёт о том, что файловую систему контейнера нельзя использовать даже как временный буфер для постоянно записываемой информации. Будь то логи или любые другие файлы. Так устроена файловая система контейнера - она будет "пухнуть" даже если файлы будут удаляться. Выходов много разных, помимо лучшего (всё писать в stdout): монтировать эфемерные тома с ноды, или persistent storage, или писать в elastic, всё зависит от конкретных случаев.
    Изменения структуры БД, добавление и изменение пользователей, создание очередей/топиков, warmup приложения и т.д. должны происходить силами приложения через git репозиторий. Тяжелые запросы могут выполняться вручную, но они также должны быть зафиксированы в миграциях.
    В приложениях должна быть реализована функция проверки работоспособности приложения, например, через Healthcheck URL, возвращающий код ответа 200, если с приложением все хорошо.
    Для возможности эффективно масштабировать приложение необходимо, чтобы оно отдавало метрики в формате Prometheus, это могут быть в том числе бизнес метрики.
    Желательно реализовать поддержку систем Application Performance Metrics и трейсинга. Например, Newrelic, Datadog или любое другое self-hosted решение.
    Каждый сервис должен иметь свою базу данных. Общение между сервисами должно быть реализовано либо через API, либо через брокер сообщений.
